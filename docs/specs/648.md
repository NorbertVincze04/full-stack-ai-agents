# Spec 648 - Booking calendar and top bar

## Summary
Home page (`/`) shows an always-visible calendar and, below the existing header, a new top bar. Users pick a bookable date; it appears on the left of the bar. The right holds a `Book Now` button that becomes `Withdraw booking` for a date the user has booked; it stores/deletes that date for the logged-in user. Anonymous users clicking it get the error `You must log in first`.

## Scope
- Frontend: top bar and calendar on the home route, booking state, calls to new booking endpoints.
- Backend: JWT-verifying middleware (none exists), booking endpoints, bookings repository/service/controller, tests.
- Database: `bookings` shaped as "one booking per user per date" in both schemas (migration files only; see Risk gate).

## Out of scope
- Desk selection UI, admin booking management, booking history, e-mail notifications, capacity limits.
- Changing login/register, the existing header, the rate limiters, or the nginx `X-Forwarded-For` gap.
- Fixing the missing `deskbookingPrj` tag on work item 648 (ingestion concern).

## Area
- `frontend`: calendar, top bar, button states, error message (new lazy `booking` feature on `/`, which has no route today).
- `backend`: persistence and auth check are required; the front end cannot store the booking alone (`docs/context/backend.md`: no code uses `bookings` yet, no auth middleware exists). The migration files live in `Backend/` and belong to this area.
- `containers`: not needed; no compose, `.env`, image or `apiUrl` change. The local `db` container already has `"ico-env".bookings`; its reshaping is a backend migration file applied by a human to existing volumes.
- `pipelines`: not needed.

## Scope flags
- `ui-changes`: yes - new top bar, calendar, home route.
- `logic-changes`: yes - date rules, booking and withdraw logic, auth check.
- `security-relevant`: yes - authenticated endpoints, JWT verification, per-user data, SQL; only the user id is stored (no e-mail).
- `dependencies-changed`: no - custom calendar grid, JWT verification with the existing `jsonwebtoken`.
- `database-changes`: yes - new `public.bookings` migration and a reshaping migration for `"ico-env".bookings`.
- `scaffolding-only`: no.

## Functional requirements
- FR1. `/` renders a month-grid calendar and, above it and below the existing header, a top bar; both always visible, no toggle. Other routes show no bar.
- FR2. Bookable dates: 4 weekdays starting today if today is a weekday, otherwise starting at the next weekday (Mon-Fri only). Every other day (past, Saturday, Sunday, beyond the window) is visibly disabled and not selectable by mouse or keyboard.
- FR3. On load the first bookable date is preselected; selecting another bookable date shows it on the left of the top bar as e.g. `Mon, 9 Nov 2026`.
- FR4. Right of the top bar: button `Book Now`; after booking `Withdraw booking`. The label follows the selected date (booked -> `Withdraw booking`, not booked -> `Book Now`).
- FR5. Logged in and no booking for the selected date: click calls `POST /api/bookings`; on success the button becomes `Withdraw booking`. A user may hold bookings for several dates.
- FR6. Logged in with a booking for the selected date: click calls `DELETE /api/bookings/<date>`; on success the button returns to `Book Now`.
- FR7. Not logged in: click makes no API call and shows `You must log in first` in the top bar area; the user is not redirected.
- FR8. For a logged-in user the booked dates are loaded on page load (`GET /api/bookings/mine`), so button state survives reload.
- FR9. Backend rejects dates in the past, weekend days and dates outside the 4-weekday window (400), using the server date; the client rules are not trusted.
- FR10. Backend identifies the user only from the verified JWT (never from the request body); missing/invalid/expired token -> 401. The user key stored is the token's `id` claim (user id, uuid); the e-mail is never stored in `bookings`.
- FR11. Withdraw deletes only the caller's own booking for that date (`WHERE` on date and `user_id`); unknown booking -> 404.
- FR12. Booking a date the user already holds -> 409; frontend shows a generic error. Different users may book the same date.
- FR14. Booking for a user id that no longer exists in `users` (FK violation) -> 401, no booking stored.
- FR13. Session expiry while on the page: a 401 response clears the session via `AuthService` and shows `You must log in first`.

## API / data changes
| Method, path | Auth | Request | Responses |
| --- | --- | --- | --- |
| `POST /api/bookings` | JWT | `{ date: "YYYY-MM-DD" }` | 201 `{ success, payload: { booking } }`; 400 validation; 401; 409 |
| `DELETE /api/bookings/:date` | JWT | none | 200 `{ success }`; 400; 401; 404 |
| `GET /api/bookings/mine` | JWT | none | 200 `{ success, payload: { bookings: [{ date }] } }`; 401 |

- Same response shape `{ success, payload?, message?, errors? }`; parameterised SQL; schema-aware table name as in `userRepository`.
- Data: `bookings.user_id uuid` references `users(id)` (`ON DELETE CASCADE`); uniqueness is `UNIQUE (booking_date, user_id)`; no e-mail or name stored. `booking_desk` and `user_name` are no longer used by code (nullable in the container table, absent in `public`).
- `public` schema: new `Backend/migrations/` file creating `bookings` (`id`, `user_id uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE`, `booking_date date NOT NULL`, `created_at`, `UNIQUE (booking_date, user_id)`, index on `user_id`) with `CREATE TABLE IF NOT EXISTS`, human-applied after `001_create_users.sql`.
- Container schema `"ico-env"`: new `Backend/db/migrations/004_*.sql`, idempotent, registered in `schema_migrations`: add `user_id uuid REFERENCES "ico-env".users(id) ON DELETE CASCADE` (nullable, so any legacy row survives; code always sets it), make `booking_desk` and `user_name` nullable, drop `UNIQUE (booking_date, booking_desk)`, add `UNIQUE (booking_date, user_id)` and an index on `user_id`. No column is dropped and no data deleted. Init SQL only runs on an empty volume, so existing volumes need it applied by hand; `003` is not edited.
- Auth middleware verifies the HS256 JWT with `JWT_SECRET` (claims `id`, `email`, `type`); it is injectable into `createApp` for tests.

## UI behaviour
- Top bar: selected date left, button right; wraps on narrow screens (320 px).
- Calendar: keyboard operable, disabled days have `aria-disabled`, selected day has `aria-pressed`/`aria-selected`; error text in an `aria-live` region.
- Button is disabled while a request is in flight.

- [ ] AC5: `Withdraw booking` removes the booked date for that user and the button returns to `Book Now`; other dates and other users' bookings stay untouched.

- [ ] AC7: A booking survives a page reload for the logged-in user (button state reflects it); a user can hold several dates and the button follows the selected date.
- [ ] AC8: Backend and frontend tests cover FR2, FR5-FR7, FR9-FR12, FR14; `npm test`, `npm run build`, `npm run test:ci` pass.
- [ ] AC9: Migrations for `public.bookings` and `"ico-env".bookings` are added (not run by agents); context files (`backend.md`, `frontend.md`, `project.md`, and `containers.md` if its table description changes) updated.

## Risks
- Date window uses the server date; a client in another time zone may see a mismatch near midnight.
- Booking endpoints are not behind the rate limiter; behind nginx all clients share one `req.ip` (known gap).
- JWT lives in `sessionStorage` (accepted earlier).
- Existing local DB volumes keep the old constraint and lack `user_id` until `004` is applied by hand; booking fails with a DB error until then.
- `public.bookings` needs `public.users` to exist first (FK); a deleted user's bookings are removed by cascade (no user-delete feature exists).

## Risk gate
- R1 (security): new JWT-verification middleware and authenticated endpoints; user identity is taken from the token. Impact: auth bug exposes or lets users delete others' bookings. Safer alternative: none cheaper; keep it minimal, token only, tests for 401/ownership.
- R2 (database): new `public.bookings` migration (with FK to `users`) and a `004` migration on the container table that adds `user_id` + FK, drops the old unique constraint and relaxes `booking_desk`/`user_name` (both human-applied, not run by agents). Impact: schema change on a table that could hold data; drift between Cloud Foundry and container if only one is applied. Safer alternative: `public` migration is create-only; `004` is idempotent, never edits `003`, drops only the unused `(booking_date, booking_desk)` constraint (no code uses it), drops no column, deletes no data; back up before applying on a volume with data. Approved as described.
- R3 (security/personal data): resolved - the safer alternative was chosen; bookings store the user id, never the e-mail (Q3 B).
