# Spec 650 - desk numbering

## Summary
Desks are grouped in categories A to D with 4 desks each and shown as A1-A4, B1-B4, C1-C4, D1-D4 (16 desks). Today there are 12 desks (`D01`-`D12`, 4 x 3 plan). Existing desks are deleted and recreated (D1).

## Scope
- Desk table content (ids and labels) in the DB and everywhere a desk is shown (plan, booking list, booked-by info, messages).
- Plan shows 4 blocks (one per letter) of 2 x 2 desks.

## Out of scope
- Roles, desk types, per-category rules, desk management UI, changes to the 4-weekday window.
- Restoring the desk of existing bookings.

## Area
`frontend`, `backend` (the database change is part of `backend`). `containers`: only the init SQL in `Backend/db/migrations` needs a new file (no compose or image change).

## Pipeline scope
n/a

## Scope flags
- `ui-changes`: yes - plan layout (4 blocks of 2 x 2) and desk labels.
- `logic-changes`: yes - desk ids change; existing bookings lose their desk link (`booking_desk` NULL) and must display without a desk.
- `security-relevant`: no.
- `dependencies-changed`: no.
- `database-changes`: yes - new migration (UPDATE of `bookings`, DELETE and INSERT of `desks`).
- `scaffolding-only`: no.

## Functional requirements
- FR1: 16 desks exist, 4 per category A-D, numbered 1-4 within the category; ids equal labels (`A1` ... `D4`) (A1).
- FR2: A desk label is `<letter><number>` (A1 ... D4).
- FR3: `GET /api/desks` returns the new desks, ordered by category then number.
- FR4: Plan renders one 2 x 2 block per letter (A1 A2 / A3 A4); A and B in the upper half, C and D in the lower half (A2). Labels only, no headings (D3).
- FR5: Existing bookings are kept but `booking_desk` is set to NULL; they stay listed (date, user) without a desk label.
- FR6: New migration deletes and recreates the `desks` data, guarded so a second run changes nothing (backend `migrations/` and container `db/migrations/`), like 004/005.
- FR7: FK to `desks` and index `ux_bookings_date_desk` stay.

## API / data changes
- `desks`: 12 rows deleted, 16 inserted (`id` = label, `grid_row`/`grid_col` 1-4 so blocks form 2 x 2 groups).
- `bookings.booking_desk`: set to NULL for all rows before the delete (FK has no `ON DELETE` action and would block it); column and FK stay.
- API shape unchanged (`id`, `label`, `row`, `col`); booking `desk` value is a desk id (now `A1`...`D4`).

## UI behaviour
- Plan: 4 blocks (A, B / C, D), each 2 x 2 desks, labels only; availability, selection, booked-by text unchanged.
- A booking without a desk is listed without a desk label and marks no desk as taken.

## Acceptance criteria
- AC1: `GET /api/desks` returns 16 desks with labels A1-A4, B1-B4, C1-C4, D1-D4, ordered A1..D4.
- AC2: The plan renders all 16 desks with these labels as 4 blocks of 2 x 2 desks (one block per letter), labels only, no letter headings.
- AC3: Desk selection, booking, withdraw and availability work for every desk, including a desk such as `C3`.
- AC4: A booking made before the change is still listed after the migration, without a desk label (`booking_desk` NULL); it blocks no desk.
- AC5: The migration deletes no booking and sets `booking_desk` to NULL only in the first run; running it twice gives the same result without error (a booking on a new desk made between runs keeps its desk).
- AC6: Existing backend and frontend specs are adapted and pass; tests cover 16 desks, the labels, the 2 x 2 blocks and a booking without a desk.

## Risk gate
- R1 (database, human-approved, D1): the migration sets `bookings.booking_desk` to NULL for all bookings (UPDATE), DELETEs all `desks` rows and inserts 16 new ones. Impact: existing bookings permanently lose their desk link; ids `D01`-`D12` disappear (API values change); FK and `ux_bookings_date_desk` stay (rows without desk are ignored by the index). Safer alternative: keep ids `D01`-`D12`, update only `label` with a narrow `WHERE id = ...`, add `D13`-`D16`, bookings untouched. Mitigation: `pg_dump` first, applied by the human, idempotency guard.
- R2 (database): destructive migration (UPDATE + DELETE) for the local container and the human-applied database; never run by agents or the app. Safer alternative: the additive-only migration of R1; rollback only via the `pg_dump` backup.

## Decisions
- D1: Q1 = c) delete and recreate all desks; chosen knowingly by the human, accepting that existing bookings lose their desk link. Safer alternative stays listed in R1.
- D2: Q2 = c) 2 x 2 blocks per letter.
- D3: Q3 = a) no headings, labels only. Q2c suggested letter headings; the human chose labels only, so blocks are visual groups without headings.
- D4: Q4 = b) the missing Azure tag is ignored.

## Assumptions
- A1: Recreated ids equal the labels (`A1`...`D4`); `varchar(10)` is enough.
- A2: Block order: A top-left, B top-right, C bottom-left, D bottom-right.
- A3: Blocks are separated visually (spacing), without headings (D3).
- A4: Bookings with `booking_desk` NULL are already valid (004); the tests confirm the UI shows them without a label.
